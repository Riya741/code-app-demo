## 2. The unifying idea: one feature, five lenses

Rather than five unrelated demos, add **one AI capability** to the app and build it in a way that exercises every topic:

> **AI Account Brief.** In the Executive Summary panel, a *Draft with AI* button runs a multi-agent pipeline over the
> customer's use cases and events. It produces a cited, sanitised draft summary that the user reviews in the existing
> rich-text editor and then saves. This also closes the open High gap **SUM-EDIT-001** (persist the summary).

```
                      ┌──────────── Topic 1: specs 022–026, agent specs, hand-off contracts, Article XII ────────────┐
                      │                                                                                             │
 Developer ─▶ Claude Code (Topic 2: CLAUDE.md, subagents, skills, plan mode, worktrees, headless CI review)          │
                      │        ▲ hooks + skills + MCP (Topic 5: spec-guard hooks, sdd-toolkit plugin, workbook MCP)  │
                      ▼        │                                                                                     │
               App: "Draft with AI" ──▶ Orchestrator (Topic 4) ──▶ Retriever → Analyst → Writer ⇄ Critic → Guard     │
                                               │  retries · circuit breaker · checkpoints · budgets · traces         │
                                               ▼                                                                     │
                                  Eval harness (Topic 3): golden set, code graders, LLM-as-judge, judge calibration, │
                                  model/prompt comparison → ADR-0007 decision → G7 regression gate in CI ────────────┘
```

The same tool functions (search customer, list use cases, list events, get requirement) are written once in
`server/ai/tools.ts` and exposed two ways: to the runtime agents through the Anthropic SDK, and to Claude Code
through the MCP server. That shared code is the "reusable" evidence for Topic 5.

## 7. API budget: $50 for Phases 3 and 4

**Yes, $50 covers both phases**, if each run is sized deliberately. Phase 3 should cost almost nothing: tests use a
fake client. Most of the money goes on Phase 4, and in Phase 4 the judge costs about as much as generating the briefs.

### Unit costs (estimates; the Phase 4 pilot replaces them with measured numbers)

Prices per 1M input / output tokens: Haiku 5.5 $0.10 / $0.50 · Sonnet 5.5 $2 / $10 · Opus 5.5 $4 / $20. The Batch
API halves every price. Token estimates assume a typical fixture customer (about 7 use cases and 5 events) and
include adaptive thinking.

| Item | Tokens (in / out) | Haiku | Sonnet | Opus |
|---|---|---|---|---|
| One brief, critic **on** (Analyst, Writer, Critic, ~40% need one revision) | ~24K / ~6K | $0.005 | $0.11 | $0.22 |
| One brief, critic **off** | ~11K / ~3.5K | $0.003 | $0.06 | $0.11 |
| One judgement (data + brief + rubric → evidence, reasoning, scores) | ~8K / ~3K | — | $0.046 | $0.092 |

### Allocation

| Use | Size | Est. cost |
|---|---|---|
| Phase 3: live development runs | ~60 briefs, mostly Haiku and Sonnet, a few Opus | $5 |
| Phase 4: pilot | 3 cases × 3 models, to measure real tokens before anything bigger | $1 |
| Phase 4: judge calibration | 20 outputs × ~4 judge-prompt versions | $5 |
| Phase 4: experiment matrix, generation (Batch) | 6 configs × 30 cases × 2 repetitions = 360 briefs | $15 |
| Phase 4: judging the matrix (Batch) | Sonnet judge on all 360, Opus judge on a 20% sample | $12 |
| Phase 4: pairwise prompt v1 vs v2 (Batch) | 30 cases × 2 orders | $2 |
| **Planned** | | **$40** |
| Reserve | Re-runs, a few live G7 smoke runs (~$1 each), surprises | $10 |

The original plan (12 configs × 3 repetitions, Opus judge on everything) would cost about $120, so the matrix is
cut to the 6 configs that still answer the three questions the ADR needs:

| Question | Configs compared |
|---|---|
| Which model? | Haiku, Sonnet, Opus, each with prompt v2 + critic on |
| Did the prompt change help? | Sonnet v1 vs Sonnet v2 (critic on) |
| Is the critic worth its cost? | Critic on vs off, on Sonnet and on Haiku |

### Rules that keep it inside $50

1. **Set a $50 spend limit on the API key's workspace in the Claude Console**, so the key cannot overspend whatever the code does.
2. **Keep this key out of Claude Code.** Claude Code should run on your own Claude login. If Claude Code is signed in with this API key, everyday development would use up the credit within days.
3. **Tests and CI never call the API.** Unit and fault-injection tests use a fake client and recorded responses. In CI, G7 runs the code graders on recorded outputs on every PR; the live eval smoke run and the headless `claude -p` review are manual triggers only.
4. **A spend ledger with a hard stop.** Every API call appends its `usage` and cost to a ledger. Each script prints its projected cost and refuses to start if that would exceed what is left. This doubles as evidence for budgets in Topic 4 (AOPS-BUDG-001).
5. **Pilot first, then batch.** Measure 3 cases, update the table above with real numbers, then send the bulk through the Message Batches API.
6. **Cache the stable prompt prefix** (system prompt, agent spec, rubric) wherever it is long enough to be cached.
7. **Store the key in `.env` only.** It is gitignored. In GitHub, store it only as an Actions secret, used by the manual workflows.
